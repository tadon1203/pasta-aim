# 追従性能改善計画

ステータス: 実装中

- 実装済み: 1-1（トレースログ）、1-2（ループ指標の UI 表示）、1-3（ターゲット ID 追跡）、2-1（端数の繰り越し）
- 未実装: 1-4（キャリブレーション）、2-2、2-3、フェーズ 3〜5

## 目的

ゲームの fps を上げずに、追従誤差（遅れ・ノコギリ波・オーバーシュート）を減らす。
体感ではなく、計測とオフライン評価で判断できる状態を先に作る。

## 現状の制御モデル

- `engine/output.rs` の `plan()` は比例制御: 送信量 = 誤差 × gain（`Sensitivity`）。
- `MotionGate` により「送信完了後に表示されたフレーム」だけを使うため、ループは直列で、
  補正周期 = ループレイテンシ L（通常ゲームフレーム間隔 Tf の 2〜4 倍）。
- 等速で動くターゲットに対する定常誤差 ≈ v·L / K（K = gain）。

L の内訳:

```
[表示] → ① capture 取得 → ② GPU コピー＋前処理 → ③ キュー待ち → ④ 推論
       → ⑤ 後処理＋MAK 送信 → ⑥ USB→PC→ゲームの入力読み取り
       → ⑦ ゲーム処理・描画・表示 → ⑧ 次の表示フレーム待ち
```

- ①〜⑤: 計測済み（`FrameReport`、`inference_worker.rs`）。
- ⑥〜⑧: 未計測。以降これを D（送信完了 → 画面に反映されるまで）と呼ぶ。

## 方針と却下した案

| 案 | 判断 | 理由 |
|---|---|---|
| 推論 1 回に対して送信を多数回に分ける | 却下 | ゲームは 1 フレームに 1 回しか入力を読まないため、合計を 1 回送るのと同じ。送り続ける方式ではゲインが L の揺らぎに依存しオーバーシュートする |
| ゲートを単に外して感度を下げる | 却下 | 安定のためゲインを約 K/d に下げる必要があり、定常誤差は v·L/K のまま |
| 同一フレームへの複数回推論 | 却下 | 決定的なので意味がない |
| 速度予測 / Kalman | 保留（原則やらない） | ゲームキャラクターは慣性がほぼなく、反転で予測なしより悪化する（最大約 2v·L）。微分でノイズが増幅され、フィルタすると遅れる。自分の補正・ユーザー操作・距離変化・ターゲット切り替えが速度推定を汚す。物理マウスの移動量は MAK から取得できない（`vendor/protocol/KM_API.md`: ストリームはボタンのみ） |
| ゲート撤去＋Smith predictor | 採用 | L は変わらないが、補正周期が L から Tf に短縮され、補正回数が 2〜4 倍になる |
| こちら側の遅延（①〜⑤）削減 | 採用（計測次第） | 遅延はゲームフレーム単位で切り上がるため、入力読み取りの境界を越えれば 1 フレーム短縮できる |

## フェーズ 1: 計測基盤（既存挙動は変えない）

### 1-1. フレームごとのトレースログ

- 記録項目: `present_qpc`、全検出（選ばれなかったものも含む）、選ばれたターゲット、
  `plan` の計算値（丸め前）、実際の送信量、`output_complete_qpc`、ゲートで捨てたか。
- 捨てたフレームはキャプチャスレッド側で落ちるので、その件数もトレースに含める。
- リングバッファに溜め、ホットキーまたは停止時に `logs/` へ書き出す。
  フレームの処理経路では書き込みのみ、ファイル I/O は別スレッドで行う。
  `StatusHub` と同じくフレームの処理経路でブロックしない。
- 形式: 1 行 1 フレームの CSV か JSON Lines（オフライン評価で読みやすいもの）。

### 1-2. ループ指標を UI に表示

- ループ周期（有効な送信の間隔）
- ゲートで捨てたフレームの割合（`MotionGate::take_discards` は既存）
- ロック中の誤差の RMS
- オーバーシュート回数（誤差の符号反転）
- 捕捉してから収束するまでの時間

### 1-3. ターゲットの ID 追跡

- 前フレームとの IoU で簡単に対応付けする。
- ターゲット切り替えを検出して指標から除外する。後段のリセット条件にも使う。

### 1-4. キャリブレーション（D と px/count）

- 練習場などで動かない的を捕捉した状態で、既知のカウント（例: +200）を送る。
- 送信完了から検出ボックスが最初に動いたフレームまでの時間を D、
  移動量（px）÷ 送信カウントを px/count とする。
- 複数回、水平・垂直それぞれで測り、分布（平均・ばらつき・山が 2 つあるか）を記録する。
- D の分布に 1 フレームずれた山が 2 つあれば、入力読み取りの境界付近にいるので、
  ①〜⑤ の削減が効く可能性が高い。
- 結果は設定に保存する（範囲外の値はデフォルトに戻る既存ルールに従う）。

## フェーズ 2: 小さく確実な改善

### 2-1. 端数の繰り越し

- `quantize()` の丸め残差を次フレームに持ち越し、低ゲイン時の不感帯をなくす。
- 実行開始・ターゲット切り替え・ターゲット喪失でリセットする。

### 2-2. 換算とゲインの分離

- 現状の `Sensitivity` は「ゲイン」と「px→count 換算」を兼ねている。
- `px_per_count`（キャリブレーション値）と `gain`（誤差のうち 1 回で詰める割合、
  1.0 で 1 回で誤差をゼロにする）に分ける。
- 設定の移行はしない方針なので、既存の `sensitivity` の扱いを決める
  （例: 新しい項目を追加し、欠けている場合はデフォルトを使う）。

### 2-3. 検出ブレの抑制（任意・弱め）

- ボックス中心に軽い平滑化をかける。強くすると遅れになるので、トレースで比較して決める。

## フェーズ 3: オフライン評価ハーネス

- トレースを読み込み、制御器の案を比較する。
- 単純なモデル（遅延 D ＋換算 px/count ＋ターゲット軌道）によるシミュレータを作る。
  等速・反転（ADAD）・停止の軌道を用意する。
- 比較する案: 現行ゲート方式、Smith predictor（ゲイン違い）、D・px/count を
  わざとずらした場合（ずれへの耐性を確認するため）。
- `cargo test` またはデバッグ用の bin として実装し、ゲームを起動せずに調整できるようにする。

## フェーズ 4: ゲート撤去＋Smith predictor

### 仕組み

1. 送信ごとに `(complete_qpc, dx, dy)` を送信履歴に記録する。
2. 各フレーム（`present_qpc = t`）で:
   ```
   未反映分 = Σ 送信履歴のうち complete_qpc > t − D のもの
   補正誤差 = 観測誤差 − 未反映分 × px_per_count
   送信量   = gain × 補正誤差 / px_per_count
   ```
3. 確実に反映された古い記録は捨てる。

### 変更点

- `MotionGate` をキャプチャ・推論の両スレッドから外す（または設定で切り替えられるようにし、
  比較用に旧方式を残す）。
- 送信履歴は推論スレッドだけが持つ（出力は推論スレッドで行っているため共有不要）。
- 実行開始・出力方式（injection API）の変更・ターゲット切り替えで履歴をリセットする。
  現行の `MotionGate::reset` と同じタイミングにする。
- コントローラー出力はスティックの値（速度指令）なので、そのまま同じ式には乗らない。
  まずマウス出力のみを対象とし、コントローラーは現行方式のままにする。

### ずれたときの挙動

- D・px/count が小さすぎる → 未反映分を引ききれず二重補正 → オーバーシュート。
- D・px/count が大きすぎる → 反映済みの分まで引いてしまい補正不足 → 追いつきが遅い。
- 現行ゲートは「D = 0 と仮定し、反映されるまで待つ」特殊ケース。⑥⑦ の分は既に漏れている可能性がある。

### 完了条件

- フェーズ 3 のシミュレーションで、現行方式より RMS 誤差とノコギリ波の振幅が小さい。
- 実機のトレースで、オーバーシュート回数が現行方式以下、ループ周期がほぼ Tf。

## フェーズ 5: こちら側の遅延削減（計測結果次第）

- フェーズ 1-4 の D の分布を見て、境界付近にいる場合のみ優先して取り組む。
- 候補: 推論時間（モデル・入力サイズ・FP16・`low_latency`）、前処理、キュー待ち、MAK 書き込み。
- 効果は「1 フレーム短縮できたか」で判断する（境界を越えない削減はほぼ効果なし）。

## ユーザー側の設定（コード変更なし、README に記載）

- ゲーム内の低遅延モード（Reflex / Anti-Lag）を有効にする。
- VSync オフ、fps 上限はゲーム内のリミッターで掛ける。
- ボーダーレスで independent flip / MPO が効いているか確認する。

## 予測について（将来やるなら）

原則やらない。やる場合はフェーズ 4 が完了し、換算・送信履歴・毎フレーム観測が揃ってからにする。

- 同じ方向の速度が N フレーム続いたときだけ有効にする。
- 予測量は v·L の一部（30〜50%）で、上限を付ける。
- 反転の兆候・ターゲット切り替えで即リセットする。
- 必ずフェーズ 3 のハーネスで、反転軌道を含めて予測なしより良いことを確認してから入れる。
